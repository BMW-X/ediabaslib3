Fork changes

This page describes how the anykee-v2 branch differs from the upstream EdiabasLib project, why each change exists, and what you need to update in code that calls the library.

Fork baseline

The fork starts from a single upstream commit and adds two commits on top of it. The following table identifies both sides so that you can reproduce the comparison.

Structured error reporting

Commit 2a6186bc8 changes how the interpreter reports errors. The goal is to let a host application react to an error from the exception alone: the exception carries the EDIABAS error code, the EDIABAS error text, the member that reported the error, and any context values, such as the name of a missing ECU file.

Top-level exception class

Upstream declares EdiabasNetException as a class nested inside EdiabasNet. The fork moves it to its own file, EdiabasNetException.cs, as a top-level class in the EdiabasLib namespace, and adds the Args property and a second constructor.

Upstream

public partial class EdiabasNet
{
    public class EdiabasNetException : Exception
    {
        public EdiabasNetException(string message,
            ErrorCodes errorCode) : base(message)
        {
            ErrorCode = errorCode;
        }

        public ErrorCodes ErrorCode { get; private set; }
    }
}

Fork

public class EdiabasNetException : Exception
{
    public ErrorCodes ErrorCode { get; init; }
        = ErrorCodes.EDIABAS_ERR_NONE;
    public Dictionary<string, object> Args { get; init; }
        = new Dictionary<string, object>();

    public EdiabasNetException(string message,
        Exception innerException = null)
        : base(message, innerException) { }

    public EdiabasNetException(string message,
        ErrorCodes errorCode,
        Dictionary<string, object> args = null)
        : base(message ?? errorCode.ToString())
    {
        ErrorCode = errorCode;
        HResult = (int)errorCode;
        if (args != null) { Args = args; }
    }
}

The following table compares what the exception carries in each version.

MemberUpstreamFork
Full type nameEdiabasLib.EdiabasNet+EdiabasNetExceptionEdiabasLib.EdiabasNetException
ErrorCodeThe EDIABAS error code.Unchanged. The setter is now init instead of private set.
ArgsNot available.Context values for the error. Empty when the error site passes none; never null.
MessageError occurred: EDIABAS_IFH_0009IFH-0009: NO RESPONSE FROM CONTROLUNIT
HResultThe .NET default for Exception.The integer value of the error code, for example 92 for EDIABAS_SYS_0002.
SourceThe .NET default, which is the assembly name.The name of the member that called SetError, for example OpTabsetex.

The interpreter itself only uses the constructor that takes an error code. The constructor that takes an inner exception exists for host code that wants to wrap its own failures; an exception created that way has ErrorCode set to EDIABAS_ERR_NONE.

SetError and RaiseError signatures

Both methods gain optional parameters that carry the context into the exception.

Upstream

public void SetError(ErrorCodes error)

public void RaiseError(ErrorCodes error)

Fork

public void SetError(ErrorCodes error,
    Dictionary<string, object> args = null,
    [CallerMemberName] string source = null)

public void RaiseError(ErrorCodes error,
    Dictionary<string, object> args = null,
    string source = null)

The values flow as follows:

  1. An opcode or an interface handler calls SetError. The compiler fills in source with the name of the calling member.
  2. If the running job hasn't masked the error with the BEST/1 error trap, SetError passes args and source to RaiseError. A masked error discards both.
  3. RaiseError creates the exception with the EDIABAS error text as the message, stores args in Args, and assigns source to Source.

Six opcode sites in EdOperations.cs call RaiseError directly and don't pass a source. For those errors, Source keeps the .NET default. The ErrorRaisedFunc callback still receives only the error code; read Args from the exception.

Warning: The C# compiler resolves optional parameters at the call site. An assembly that was compiled against the upstream EdiabasLib.dll and calls SetError(ErrorCodes) or RaiseError(ErrorCodes), such as a custom interface handler, throws MissingMethodException when it runs against the fork. Recompile every such assembly against the fork.

Exception messages

Upstream formats the message from the enum name. The fork uses the text that EdiabasNet.GetErrorDescription returns, which is the same text that the original EDIABAS shows.

Error codeUpstream messageFork message
EDIABAS_IFH_0009Error occurred: EDIABAS_IFH_0009IFH-0009: NO RESPONSE FROM CONTROLUNIT
EDIABAS_SYS_0002Error occurred: EDIABAS_SYS_0002SYS-0002: ECU OBJECT FILE NOT FOUND
EDIABAS_SYS_0018Error occurred: EDIABAS_SYS_0018SYS-0018: END JOB ERROR

Don't parse the message to identify an error. Compare ErrorCode with a member of EdiabasNet.ErrorCodes instead.

Error arguments

The fork passes arguments at two error sites, both in the tabsetex opcode (OpTabsetex in EdOperations.cs). An ECU file runs this opcode to read a table from another ECU file, and the opcode reports EDIABAS_SYS_0002 when it can't find or open that file.

SituationKeyValue
Neither <name>.prg nor <name>.grp exists in EcuPath.filenameThe full path of the .prg file that the opcode looked for.
The file exists, but the library can't open it.filenameThe full path of the file that failed to open.
baseFileNameThe file name that the ECU file requested, without directory or extension.

All other error sites pass no arguments.

Note: These arguments describe a file that a running job refers to. When the ECU file that you pass to ResolveSgbdFile or ExecuteJob is missing, the library throws ArgumentOutOfRangeException, not EDIABAS_SYS_0002. See Exceptions that aren't EDIABAS errors.

The following example uses the arguments to report which table file is missing:

try
{
    ediabas.ExecuteJob("FS_LESEN");
}
catch (EdiabasNetException ex) when (ex.ErrorCode == EdiabasNet.ErrorCodes.EDIABAS_SYS_0002)
{
    string missing = ex.Args.TryGetValue("filename", out object value) ? value as string : null;
    Console.WriteLine($"{ex.Message} ({missing ?? "unknown file"}), reported by {ex.Source}");
}

Exceptions from ExecuteJob keep their type

Upstream wraps every exception that isn't an EdiabasNetException in a plain System.Exception before it leaves the job. The fork rethrows the original exception in two places: the job loop behind ExecuteJob, and the identification job that ResolveSgbdFile runs for a group file.

Upstream

catch (Exception ex)
{
    LogString(EdLogLevel.Error,
        "executeJob Exception: " + GetExceptionText(ex));
    if (ex is EdiabasNetException)
    {
        throw;
    }
    throw new Exception("executeJob", ex);
}

Fork

catch (Exception ex)
{
    LogString(EdLogLevel.Error,
        "executeJob Exception: " + GetExceptionText(ex));
    throw;
}

This has the following consequences for a host:

  • A transport failure, such as an IOException from a serial port, reaches your code with its own type and its original stack trace. In upstream, you find it in InnerException of an exception with the message executeJob or executeIdentJob.
  • When AbortJobFunc returns true, the interpreter throws an Exception with the message executeJob aborted. In the fork, that exception reaches your code directly. In upstream, it's the InnerException of the executeJob wrapper.
  • The exit job, the base job, and the virtual jobs (for example _JOBS) still wrap non-EDIABAS exceptions in System.Exception, as in upstream.

The xstopf opcode on a closed channel

Commit 8c2f61c4a changes the BEST/1 xstopf opcode (stop_frequent in BEST/2), which stops a repeated telegram.

Upstream

if ((interfaceClass == null) || !interfaceClass.Connected)
{
    ediabas.SetError(ErrorCodes.EDIABAS_IFH_0056);
}
else
{
    interfaceClass.StopFrequent();
}

Fork

if ((interfaceClass == null) || !interfaceClass.Connected)
{
    // no channel: no frequent telegram to stop
    return;
}
interfaceClass.StopFrequent();

BMW functional jobs, for example IDENT_FUNKTIONAL in f01.prg, run stop_frequent right after they hang up the connection, or between two protocol concepts over ENET. At that point the diagnostic channel is closed on purpose, and upstream fails the job with IFH-0056: ILLEGAL CHANNEL. With no open channel there is no repeated telegram to stop, so the fork treats the opcode as complete and continues the job.

Note: Only xstopf changes. The other interface opcodes, such as xsend, xstate, and xtype, still report EDIABAS_IFH_0056 when no interface handler is assigned. The fork doesn't write a trace line when it skips the opcode, so a trace from the fork has no IFH-0056 entry where a trace from upstream has one.

Target frameworks and dependencies

Commit 2a6186bc8 removes the .NET Framework targets and adds a net9.0 target to the core library.

ProjectUpstream target frameworksFork target frameworks
EdiabasLib.csprojnet10.0-windows10.0.26100.0, net8.0-windows10.0.26100.0, net48, net481net10.0-windows10.0.26100.0, net8.0-windows10.0.26100.0, net9.0

The commit also makes the following dependency changes:

  • The InTheHand.BluetoothLE and System.IO.Ports package references now apply to the net9.0 target as well as to the two Windows targets.
  • The patched Bluetooth LE build for .NET Framework is gone: Binaries/net462/InTheHand.BluetoothLEMod.dll, BluetoothLE_Patch/InTheHand.BluetoothLE.patch, and BluetoothLE_Patch/InTheHand.snk. Only the .NET Framework targets used these files.

The net9.0 target has no Windows suffix, so a project that doesn't target Windows can reference it. It compiles the same sources as the two Windows targets, including code that only works on Windows. For the limitations, see finding C4 in the code review.

Update code that calls the library

To move a host application or an interface handler from upstream EdiabasLib to the fork, do the following:

  1. Target .NET 8 or later. The fork has no .NET Framework build.
  2. Replace every reference to EdiabasNet.EdiabasNetException with EdiabasNetException. The namespace, EdiabasLib, stays the same.
  3. Recompile every assembly that calls SetError or RaiseError. No source change is needed.
  4. Replace any check of the exception message with a check of ErrorCode.
  5. Review each catch block around ExecuteJob and ResolveSgbdFile:
    • Catch EdiabasNetException first for ECU and interpreter errors.
    • Catch Exception after it for transport failures and aborts. Read the exception itself, not its InnerException.
  6. If your code relies on EDIABAS_IFH_0056 from stop_frequent to detect a closed channel, check EdInterfaceClass.Connected instead.

The following example shows a catch sequence that handles all three outcomes:

try
{
    ediabas.ResolveSgbdFile("d_motor.grp");
    ediabas.ExecuteJob("FS_LESEN");
}
catch (EdiabasNetException ex)
{
    // ECU or interpreter error with an EDIABAS error code.
    logger.Error("{Code} {Message} from {Source}", ex.ErrorCode, ex.Message, ex.Source);
}
catch (Exception ex) when (ex.Message == "executeJob aborted")
{
    // AbortJobFunc returned true.
}
catch (Exception ex)
{
    // Transport failure or internal error, with its original type.
    logger.Error(ex, "Job failed");
}

Known issues

The fork updates the core library only. The projects around it still expect the upstream API, so parts of the solution don't build. The results for EdiabasLib, ApiInternal, and EdiabasTest come from a build with .NET SDK 10.0.401 on September 30, 2026. The other rows come from reading the project files.

ProjectResultCause
EdiabasLibBuilds for all three target frameworks.Not applicable.
ApiInternalCompiler error CS0426.ApiInternal.cs, line 1447, still names EdiabasNet.EdiabasNetException. Because Api32 and apiNET depend on this project, the drop-in replacement DLLs can't be built from the fork.
EdiabasTestRestore error NU1201.The project targets net481, which can't reference the fork's EdiabasLib. Program.cs, line 280, also still names the nested exception type.
apiNET464, EdiabasLibCallNot built. Both target net481.Same framework mismatch as EdiabasTest.
EdiabasLibAndroidNetNot built. Expected to fail.The project links each source file by name, and its list doesn't include the new EdiabasNetException.cs, which EdiabasNet.cs now needs.

Two smaller leftovers are also worth knowing about:

  • EdiabasLib.csproj and Directory.Build.targets still contain item groups for net48 and net481. They never apply, and the one in Directory.Build.targets names the deleted InTheHand.BluetoothLEMod.dll.
  • The upstream code that the fork replaced remains in the source as comments, next to //at// markers. Search for that marker to find every edited site.

For an assessment of these issues and suggested fixes, see Fork changes in the code review.

Compare the fork with upstream

Run the following commands from the repository root to inspect the fork's changes yourself.

# List the fork's commits
git log --oneline ddd129427..anykee-v2

# Summarize the changed files
git diff --stat ddd129427 anykee-v2

# Show the change to one file
git diff ddd129427 anykee-v2 -- EdiabasLib/EdiabasLib/EdiabasNet.cs

# Count the upstream commits that the fork hasn't merged
git rev-list --count anykee-v2..master
