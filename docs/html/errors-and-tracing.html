Errors and tracing

EdiabasLib reports ECU and interpreter failures through EdiabasNetException and writes EDIABAS-compatible trace files. This page explains both mechanisms.

How errors propagate

  1. An opcode handler or an interface handler detects a failure and calls EdiabasNet.SetError(code, args).
  2. SetError logs the code, resets the cached group resolution so that the next call reloads the ECU file, and records the error trap bit for the code.
  3. If the running job has masked the error with the BEST/1 error trap, nothing else happens. The job reads the trap bit with its own opcodes and decides what to do. A masked error doesn't change ErrorCodeLast.
  4. Otherwise, SetError calls RaiseError. RaiseError stores the code in ErrorCodeLast, invokes ErrorRaisedFunc if you set one, and throws EdiabasNetException.
  5. ExecuteJob and ResolveSgbdFile let the exception propagate to your code.

When an error occurs while the standard exit job runs, the library reports EDIABAS_SYS_0018 instead of the original code, which matches EDIABAS behavior.

EdiabasNetException

EdiabasNetException is a top-level class in the EdiabasLib namespace.

ErrorCodes ErrorCode { get; init; }
The EDIABAS error code. EDIABAS_ERR_NONE when the exception was created without a code.
Dictionary<string, object> Args { get; init; }
Context for the error. Empty for most errors, never null. See Error arguments for the keys that the interpreter sets.
Message
The EDIABAS error text from EdiabasNet.GetErrorDescription, for example IFH-0009: NO RESPONSE FROM CONTROLUNIT.
HResult
The integer value of the error code.
Source
The name of the member that called SetError, captured with [CallerMemberName]. Errors that an opcode raises directly through RaiseError keep the .NET default.
try
{
    ediabas.ExecuteJob("FS_LESEN");
}
catch (EdiabasNetException ex) when (ex.ErrorCode == EdiabasNet.ErrorCodes.EDIABAS_IFH_0009)
{
    // The ECU didn't answer. Check the ignition and retry.
}
catch (EdiabasNetException ex)
{
    logger.Error("{Code} {Message} from {Source}", ex.ErrorCode, ex.Message, ex.Source);
}

Exceptions that aren't EDIABAS errors

ExecuteJob and ResolveSgbdFile also throw other exception types. Catch Exception after EdiabasNetException to handle them.

ExceptionCause
ArgumentOutOfRangeExceptionA job is already running, the ECU file is missing or unreadable, a group file has no matching variant, or the bytecode contains an opcode that the library doesn't implement. A missing ECU file doesn't raise EDIABAS_SYS_0002 when you call the library directly.
Exception with the message executeJob abortedAbortJobFunc returned true.
The original exception type, for example IOExceptionA transport or internal failure inside the job or the identification job.
Exception with an InnerExceptionA failure inside the exit job, a virtual job, or a job from a base file. These paths wrap the original exception.

Callbacks

PropertyDelegateWhen it runs
ErrorRaisedFuncvoid (ErrorCodes error)Inside RaiseError, before the exception is thrown. Use it to log or to collect statistics. The delegate doesn't receive the argument dictionary; read it from the exception instead.
ProgressJobFuncvoid (EdiabasNet ediabas)When the job updates InfoProgressPercent or InfoProgressText.
AbortJobFuncbool ()Polled from the opcode loop. Return true to abort. The interpreter then cancels the transmission and throws an Exception with the message executeJob aborted.

You can't change these properties while a job runs. The setters throw when JobRunning is true.

Tracing

The trace files have the same layout as the original EDIABAS traces, so you can compare a trace from EdiabasLib with a trace from a reference installation line by line.

FilePropertyWritten byContent
ifh.trcIfhTraceThe core libraryInterface connect and disconnect, communication parameters, sent and received telegrams, errors, and interpreter activity, depending on the level.
api.trcApiTraceApiInternalJob names, arguments, result sets, and errors as the API sees them. A host that references EdiabasLib.dll directly doesn't get this file.

To change the file names, set IfhTraceName and ApiTraceName.

Trace levels

The IfhTrace property takes one of the following values. Interface handlers and opcodes log through LogFormat, LogString, and LogData with the matching EdLogLevel.

IfhTraceEdLogLevelWhat the trace contains
0OffNothing.
1IfhInterface events and every telegram.
2ErrorLevel 1, plus errors.
3InfoLevel 2, plus informational messages and a line for each BEST/1 opcode that the interpreter executes.

The library discards a message whose level is above the configured IfhTrace value before it formats any text, so you can leave trace calls in hot paths.

Where trace files go

The library writes trace files to the directory in the TracePath property. The constructor sets the property as follows:

  1. On Windows, unless you pass isHosted: true, the constructor creates <assembly directory>\Trace and uses it if it's writable. Otherwise, it uses %LocalAppData%\EdiabasLib\Trace.
  2. A TracePath value from EdiabasLib.config or from the constructor string then replaces that default. The library doesn't check whether your directory is writable.

On other platforms, and when you pass isHosted: true, there is no default. Set TracePath yourself.

Trace options

  • AppendTrace=1 appends to an existing trace file, unless the file was last written more than about an hour ago. Without it, the first write in a process starts a new file.
  • IfhTraceBuffering=1, the default, buffers writes to ifh.trc. Set it to 0 when you need the last lines after a crash. TraceBuffering does the same for api.trc and defaults to 0.
  • LockTrace=1 in EdiabasLib.config blocks later changes to ApiTrace, IfhTrace, TracePath, TraceBuffering, AppendTrace, IfhTraceName, and ApiTraceName, including values in the constructor string. Use it when you deploy the library under a tool that resets the trace level. The setting has no effect in the constructor string.
  • If another process holds the trace file, the library falls back to numbered files, from ifh_1.trc to ifh_9.trc.

Differences from upstream

Error reporting is the area where this fork differs most from the upstream project. The exception type, the SetError and RaiseError signatures, the exception message, and the way ExecuteJob propagates exceptions all changed. For a before-and-after comparison and the steps to update existing code, see Structured error reporting on the Fork changes page.
